# Converge（合流）：群体共识与行动闭环工作台

## 1. 项目定位

- 目标方向：腾讯 CSIG / WXG / WorkBuddy / 腾讯会议 / 协作效率
- 当前状态：本地 MVP 0.5 已实现（讨论自动分流 + 群体协商 + 行动追踪 + DeepSeek 增强 + 合成基准对比）
- 一句话：导入一场真实讨论，系统区分“还要一起选”与“已经决定要做”；前者经过约束、Pareto 和投票形成共识，后者直接核对行动，最终持续跟踪到闭环。

本项目不是投票小程序、会议摘要工具或普通待办提取器。核心价值是用同一个可信工作流连接“形成决定”和“落实决定”：原始约束与对话可核对，系统建议可解释，最终写入必须人工确认，行动状态能够持续追踪和复盘。

## 2. 用户与问题

首批用户应选择最容易接触和访谈的群体：课程小组、学生社团、创业团队或实习项目组。

核心问题：

- 群体出游、聚餐、租房和团建时，每个人的预算、时间与不可接受条件散落在聊天中，很难系统比较。
- 多数投票容易忽略少数人的硬约束；只给一个“最佳方案”也看不见谁作出了什么妥协。
- 投票结束后还要手工确认预订、签约或分工，决定与执行经常断开。
- 任务散落在群聊和会议中，成员需要手工整理。
- “尽快处理”“下周给你”“这个我来”等表达缺少明确负责人或时间。
- 同一个任务可能被改期、转交或取消，普通抽取工具容易重复建任务。
- 自动发送提醒或创建日程可能打扰用户，甚至造成错误承诺。
- 项目管理工具记录的是结果，往往无法回到原始语境核对依据。

## 3. MVP 范围

### 必须实现

1. 以导入 `.txt`、`.md` 或结构化 `.json` 群聊/会议记录为唯一主入口，保留发言人、时间戳与原文行号。
2. 区分尚未形成共识的议题与已经形成的任务/决定；系统给出可核对草稿，不能静默创建决策或任务。
3. 对未决议题从原文预填参与者预算、距离、时间、必须/避开条件、软偏好和候选方案，支持私密预算脱敏与人工补正。
4. 用确定性代码过滤硬约束、计算逐人满意度和 Pareto 前沿；只允许对可行的 Pareto 方案做认可投票，由主持人确认最终方案。
5. 最终决定可直接创建负责人和截止时间明确的后续任务，并保留讨论、约束、投票与方案依据。
6. 识别候选任务、决策、风险和待澄清事项，并展示原文证据位置。
7. 对负责人、截止时间或动作不明确的内容生成最少必要追问，不能自行脑补。
8. 用户可逐项确认、编辑或拒绝候选任务；确认后才写入任务看板。
9. 能识别任务改期、转交、完成和取消，更新原任务而不是重复创建。
10. 提供本地提醒队列或模拟时钟，展示临期、逾期与阻塞任务。
11. 生成包含群体决策与任务证据的每日/每周闭环报告。
12. 保存约束、方案、Pareto 计算、投票、模型判断、人工审批和状态变化的审计记录。

### 可选动作

- 导出标准 `.ics` 日历文件。
- 接入一个真实但低风险的任务平台、日历或消息渠道。
- 接入腾讯会议 MCP 获取用户主动授权的会议纪要。

### 暂不实现

- 通过非官方方式抓取微信、QQ 或企业聊天数据。
- 未经确认自动给他人发送消息、建立日程或分派任务。
- 第一版处理实时音视频或自建语音识别系统。
- 通用企业办公助手、复杂组织权限系统或无评测依据的多 Agent。
- 自动编造或抓取餐厅、行程、房源价格与可用性；当前候选信息必须由人或可信来源确认。
- 用向量数据库保存全部聊天内容；只有跨会话指代确有需要时才增加检索。

## 4. 统一产品闭环

```text
导入群聊 / 会议讨论
  → 标准化消息、定位原文证据
  → 判断讨论阶段
      ├─ 尚未形成共识
      │    → 用户核对议题、约束与方案
      │    → 过滤不可行方案并展示 Pareto 妥协
      │    → 认可投票与主持人确认
      └─ 已形成任务 / 决定 / 风险
           → 补充缺失信息并审核确认
  → 创建或更新正式任务
  → 观察完成、改期和阻塞反馈
  → 调整状态并生成闭环报告
```

推荐工具接口：

- `import_conversation`
- `detect_deliberation`
- `promote_decision_candidate`
- `submit_participant_constraints`
- `add_decision_option`
- `analyze_pareto_front`
- `cast_approval_vote`
- `finalize_decision_to_action`
- `search_project_context`
- `list_current_tasks`
- `create_task_draft`
- `update_task_draft`
- `cancel_task_draft`
- `request_clarification`
- `request_human_approval`
- `commit_approved_action`
- `schedule_reminder_draft`
- `get_task_status`
- `generate_status_digest`

群体决策的硬约束永远不能被投票覆盖，系统推荐也不能替代主持人的最终确认。所有正式行动写入都应使用草稿—审批—提交三阶段；提交接口必须具备幂等键，避免重试造成重复任务或提醒。

## 5. 产品与架构原则

采用“确定性工作流 + 单 Agent”的混合架构：

- 确定性代码负责硬约束校验、满意度与 Pareto 计算、投票排序、消息格式化、时区、Schema、权限和幂等。
- 模型只增强非结构化记录中的语义判断、指代解析、候选事件分类和是否需要追问；未决议题也有保守的本地规则兜底，硬约束、Pareto、投票和最终写入均不依赖模型。
- 状态机负责新建、已确认、进行中、阻塞、完成、取消等任务状态迁移。
- 历史检索只用于解析“还是上次那个方案”等跨会话引用；简单场景直接查询结构化项目状态。
- 外部内容是不可信输入，聊天中的提示词不得改变系统规则或绕过审批。

建议技术栈：

- 当前前端：原生响应式 Web UI，以讨论导入为主入口，提供分流确认卡片、协商空间、任务看板和时间线；验证后再评估 Next.js。
- 当前后端：Python 标准库 HTTP 服务；需要多用户与部署时再迁移 FastAPI 或 TypeScript。
- 编排：显式状态图或 LangGraph，支持暂停等待人工确认和恢复执行。
- 数据：SQLite 起步；保存消息、人物别名、任务、证据、审批和审计事件。
- 模型：Provider 抽象 + 严格结构化输出，允许比较不同模型。
- 观测：记录延迟、Token、工具成功率、人工修改和错误类型。

## 6. 核心数据模型

建议至少包含以下实体：

- `DecisionDraft`：从讨论中识别出的未决议题、参与者约束、候选方案及逐字段原文位置。
- `DecisionRoom`：共同问题、场景、主持人、状态、最终方案和后续任务。
- `ParticipantConstraint`：参与者、私密预算、距离、时间、必须/避开条件与偏好。
- `DecisionOption`：方案、费用、距离、时间、标签和信息来源。
- `DecisionVote`：参与者对 Pareto 方案的认可记录。
- `Message`：发送者、时间、正文、来源位置。
- `Person`：规范姓名、群内昵称和别名。
- `CandidateEvent`：任务/已决事项/未决议题/风险/状态变化、置信度、结构化草稿和证据。
- `Task`：标题、负责人、截止时间、状态、来源和版本。
- `Clarification`：缺失字段、问题、回答与是否解决。
- `Approval`：拟执行动作、审批人、结果和时间。
- `AuditEvent`：模型版本、工具参数、执行结果和幂等键。

任务、负责人和截止时间的每个字段都应能够单独关联到原文证据或用户确认，不能只有整段摘要来源。

## 7. 数据与评测

在没有真人标注的阶段，先建立至少 50 条可复现的合成开发样例用于版本对比；它们只能用于回归和发现失败模式，不能冒充真实准确率。进入用户试用后，再建立独立的匿名真人标注集。样例覆盖：

- 明确承诺与普通讨论的区别
- 否定、玩笑、假设和引用他人话语
- “明天”“下周三”等相对时间
- 多人昵称、代词与负责人转交
- 改期、取消、完成和重复消息
- 同一任务跨多次会议持续变化
- 聊天内容中的 Prompt Injection
- 尚未达成共识、已明确拍板和仅仅列举选项之间的区别
- 多人预算、时间、距离、硬约束和候选方案的原文归属

核心指标：

- 决策室约束提交完成率、从发起到确认的耗时
- 讨论阶段分流准确率、协商草稿接受率和预填字段人工修改率
- 硬约束冲突发现率、进入投票的可行方案数、Pareto 集合规模
- 最终方案最低成员满意度、认可覆盖率和决策后反悔率
- 从最终决策到创建行动的转化率、行动按期闭环率
- 任务识别 Precision/Recall/F1
- 负责人和截止时间 Exact Match
- 新建/更新/取消分类准确率
- 错误执行率与重复任务率
- 必要澄清召回率、无效追问率
- 用户确认接受率和人工修改率
- 工具调用成功率、延迟与单任务成本
- 用户整理时间、任务遗漏率和按期闭环率

至少比较三个版本：

1. 正则/规则或单次 Prompt Baseline。
2. 结构化抽取 + 确定性校验。
3. 带项目状态、澄清和人工确认的 Agent。

真实用户指标需要实际试用后再填写，不能把目标值写成实验结果。

## 9. Definition of Done

- 新环境按照 README 可以启动前后端和评测。
- 用户导入一段未达成共识的讨论后，可以先核对协商草稿，再进入预填好的协商空间；首页没有与导入并列的第二个创建入口。
- 用户可以看到硬约束冲突、逐人满意度和 Pareto 前沿。
- 只有可行的 Pareto 方案能够被投票和最终确认；私密预算不会出现在公开状态或审计参数中。
- 最终决策可以幂等地生成一条带决策来源的正式任务。
- 用户导入一份带时间戳的对话后，可以看到逐条证据对应的候选事项。
- 已形成行动的讨论进入任务审核，未形成共识的讨论进入协商确认，两条分支最终都汇入正式任务与跟踪。
- 模糊承诺会触发澄清，未确认事项不会进入正式任务看板。
- 同一任务改期、转交或取消时不会生成重复任务。
- 模拟时间推进后能展示临期/逾期状态并生成待发送提醒草稿。
- 所有外部写操作都经过审批并留下审计记录。
- 固定评测集可一键运行 Baseline 与 Agent 对比。
- 至少完成一个真实小组的匿名化试用，或明确标记尚未完成用户验证。
